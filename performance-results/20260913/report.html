05 / 结论边界与后续对比条件

  1. Go 工程尚未实现 DNS 服务器，缺少可运行的 DNS 监听器和服务入口。没有 Go 服务端压测数据，无法判断两种实现的速度、资源效率或性能提升百分比。
  2. 本报告是 ISC BIND 基线压测与可比性说明，仅覆盖输入中列明的协议、区域数据、查询类型和速率，不等同于完整 BIND 功能测试。
  3. 配置的目标 QPS 是提供给负载工具的发送速率上限；实际发送、实际完成和目标值可能不同。这些有限速率测试不构成服务器最大 QPS 或容量上限测定。
  4. 平均延迟只统计负载工具成功完成的查询，超时或未完成查询不进入该平均数；必须同时阅读未完成比例。dnsperf 的平均值、最小值、最大值与标准差不能替代 p95 / p99，本报告未测量百分位。
  5. 每组以 3 次有效重复为设计目标，表格主值为中位数，小字为最小值–最大值。图中误差线使用相同范围，不是置信区间；不足设计重复数的组会明确标注。
  6. 这里的“未完成”对应 dnsperf 的 queries_lost，可能包含超时等情况，不能单凭该值断言网络层丢包。预热数据不并入正式测量的汇总。
  7. Go 服务尚未实现，所有 Go DNS 性能指标不可测，无法计算快慢或提升比例。
  8. 每次 5 秒、3 次重复，仅代表短时观测；不能推导最大 QPS、稳定容量或生产 SLA。
  9. 同机 Docker VM 内回环，服务端与客户端各绑定 2 个逻辑 CPU；宿主机及其他容器仍可能造成干扰。
  10. 目标发送速率不等于实际发送速率；dnsperf、CPU 和 256 个未完成请求的上限可能成为限制。
  11. 仅测试单个 unsigned 权威区的 A 和 NXDOMAIN；未测递归、DNSSEC、TLS/HTTPS、更新及传送性能。
  12. dnsperf 仅报告平均、最小、最大和标准差延迟，本报告未测 p95/p99。丢失请求不进入已收到响应的延迟统计。
  13. TCP 为每轮新建客户端连接后复用，单连接上限 100 万查询，不是每查询建连性能。
  14. CPU 为区间进程时间差，100% 表示一个逻辑核；观察窗口含客户端启动和退出等待，略长于 dnsperf 统计窗口。RSS 为每 100ms 采样所得峰值。
  15. 使用已有源码测试构建，包括 --enable-fixed-rrset、dnstap 等选项，不代表发行包默认编译性能。
  16. dnsperf 统计预期响应码；完整报文内容仅在压测前的代表性查询中核对，不能据此声明全部DNS行为兼容。
