# ADR-001：完整移植 BIND 9.20.27 到 Go

状态：实施中的技术路线；尚未完成产品兼容性验收。

日期：2026-09-13

## 目标和边界

用户要求完整移植 ISC BIND，保留全部功能。基线选用查询当日官方最新稳定版
9.20.27；开发版 9.21.25 单独记录，不混入本次兼容性基线。
“最新”在本项目中固定为此版本，后续升级必须生成新的源码清单并评估差异。

最终目标包括服务端、命令行工具、配置、持久化数据、网络协议、管理接口和可选功能。
源码逐文件清单用于追溯，不以翻译文件数量作为功能完成度。
当前只有序列号和 TTL 两个基础包，不能运行 DNS 服务。

## 决策

使用 Go 实现运行时和核心逻辑，按行为兼容迁移；保留原版 C 源码作为只读参考和测试基准。
不把启动原版 named 的 Go 包装器计为完成移植。
每个模块必须关联上游代码、测试、可观察行为和已知差异。
优先复用原版系统测试场景和输入数据；测试启动脚本可适配 Go 二进制路径，
不能为了让 Go 版本通过而改变预期结果。

## 备选方案

| 方案 | 优点 | 局限 |
|---|---|---|
| 逐行机械转换 | 容易追溯代码 | C 的内存、事件循环、宏、ABI 无法直接等价映射到 Go |
| Go 包装原版 named | 快速保留行为 | 核心仍是 C，不满足语言移植目标 |
| 按行为分模块重写（采用） | 可以使用 Go 并发、内存管理 | 必须建立充分的差分、互操作和故障恢复验证 |

## 模块顺序

1. 上游版本、源码校验、文件清单、原版可执行测试基准。
2. 序列号、DNS 名称、报文、所有 RR 类型、EDNS、配置词法与语法、zone 文件。
3. UDP/TCP/DoT/DoH 传输、权威应答、views/ACL、通配符和委派。
4. 迭代递归、转发、缓存、负缓存、DNSSEC 验证和抗攻击限制。
5. AXFR/IXFR/NOTIFY、动态更新、TSIG/TKEY/GSS-TSIG、日志和崩溃恢复。
6. DNSSEC 签名、密钥生命周期、算法、硬件密钥接口及工具链。
7. RNDC、统计、dnstap、RPZ/RRL/DNS64、catalog zones、全部工具与可选集成。
8. 完整差分测试、互操作、模糊测试、并发与资源限制、平台和性能验收。

## 验收要求

- 每个功能记录 implemented、unit-tested、differential-tested、system-tested 四个独立状态。
- 不支持的配置项必须明确报错，不能静默忽略。
- 报文比较考虑语义允许的变化；DNSSEC 签名、TTL、排序等差异必须具体解释。
- 使用本地可控的权威层级验证真实迭代递归，不能用公共 DNS 转发模拟完成。
- 验证更新/传送中断、重启、journal 恢复和密钥轮换；不能仅测正常查询。
- 模糊测试覆盖不可信报文、压缩指针、配置和 zone 文件解析。
- 记录不同平台、编译选项、外部依赖的覆盖情况；未运行不能标记通过。

## 待解决的兼容性问题

原版可选模块涉及外部 C ABI、动态数据库、DLZ、GSSAPI 和硬件密钥接口。
纯 Go 核心不自动意味着能加载原版二进制插件。需要逐接口评估兼容层或进程外桥接，
在验证前全部保持未完成；不能自行将这些功能移出范围。
平台范围和可接受的性能差异尚未确定，因此目前也不能宣称生产可替换。

## 后果

该方案需要持续工程实施。当前阶段交付的是可追溯的起点，不是完整 DNS 产品。
后续工作必须以实际测试证据更新清单，不能用本文件替代实现。
